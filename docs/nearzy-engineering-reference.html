Orientation

What Nearzy is

Three kinds of account share one API. Customers browse products from shops near a coordinate they choose; shop owners register, get verified, and list inventory; an admin curates the category tree and approves shops.

ActorJWT role claimCan do
Customer ROLE_CUSTOMER Browse and search products near a location, manage a cart and saved delivery addresses, pay via Razorpay, read their own order history, save favourites
Shop owner ROLE_SHOP_OWNER
or ROLE_SHOP		 Register a shop with a geocoded location, submit verification documents, list and edit inventory (including barcode restocking), work a triage dashboard of alerts, advance order status
Admin ROLE_ADMIN Create the hierarchical product categories, work the shop verification queue, read platform stats and an order-density heatmap

Two role names, one actor

Shop accounts exist under both SHOP_OWNER and SHOP. Registration writes SHOP_OWNER; the seed script writes SHOP; src/middleware/authorize.js treats the two as interchangeable. The Flutter client compares against ROLE_SHOP, so both paths resolve to the same shell.

Backend

Server anatomy

A conventional four-layer Express app: routes validate and unpack, services hold the logic, a DTO module shapes the response, Sequelize models own the schema. Every layer is plain CommonJS — no build step, no TypeScript.

Request pipeline

Set up in src/app.js. The notable choice is that authentication never rejects: it decodes a bearer token if one is present and moves on, leaving every access decision to the route.

cors()Reflects any origin, credentials allowed — permissive by design for device and web builds
express.json / .textBoth parsers registered: several /me endpoints post the raw JWT as a text body
authenticateVerifies the Bearer token, loads the user by email, attaches req.user = {id, email, role, rawRole}. Invalid or absent token → continues unauthenticated
router/admin · /customer · /shop · /user · /health
authorize(…roles)Per-route gate. 401 without req.user, 403 on role mismatch. Routes without it are public
serviceQueries, transactions, external calls (SMTP, Razorpay)
dto/Entities mapped to the exact shapes the Flutter models parse — productDto, orderDto, verificationDto
errorHandlerTerminal middleware translating Sequelize unique / validation / database errors into {message, status, error}

Boot sequence — src/server.js

  1. dotenv.config(), then sequelize.authenticate() — a failed connection exits the process rather than serving 500s.
  2. sequelize.sync({ alter: true }) reconciles tables with the models on every start. There are no migration files; the schema is whatever the models say.
  3. startJobs() registers the cron schedule — but only when ENABLE_JOBS=true. Off by default, because the jobs write shared state and nodemon restarts on every save.
  4. app.listen(PORT) — default 8080, with Swagger UI served at /swagger-ui and the raw spec at /v3/api-docs.

Authentication & roles

Email-and-password with bcrypt (10 salt rounds) and an emailed confirmation link, issuing a short-lived HS256 access token plus a rotating refresh token. Sessions are server-side state: refresh_tokens rows are what a sign-out revokes, so logging out is no longer just forgetting a string on the device.

ConcernImplementation
Token payload{ sub: email, name: email, role: "ROLE_<ROLE>" }
SigningHS256 with JWT_SECRET_KEY; expiry from JWT_EXPIRATION_HOURS (code default 48, .env sets 24)
Password hashbcryptjs, 10 rounds, stored in nearzy_users.password_hash

Refresh token48 random bytes, base64url. The row stores only its SHA-256 — a leaked dump must not hand out month-long sessions
RotationSingle-use. Every refresh issues a new pair and revokes the old row with revoked_reason: 'rotated'
Reuse detectionRotations of one sign-in share a family_id. Presenting an already-spent token revokes the whole family and answers 401 REFRESH_TOKEN_REUSED

The /me convention

The four profile endpoints are still POST, a carry-over from the app's earlier Spring Boot backend. They now resolve identity through utils/identity.js, which prefers the verified req.user and keeps the body token only as a fallback for older clients — the body token was never validated by the middleware, and with a rotating access token the app has no way to keep it in sync.

Payments — Razorpay

The design principle is that the client never names a price. It sends product ids and quantities; the server prices the order from its own table, opens a matching Razorpay order, and later proves the payment by recomputing Razorpay's signature.

  1. GET /customer/payment/config → {keyId, currency: "INR"}. The key secret never leaves the process; with credentials unset every payment route answers 503 and the rest of the API keeps working.
  2. POST /customer/payment/create-order with {orderItems:[{productId, quantity}], shippingAddress, billingAddress, phoneNumber}. Each line is checked for existence, availability and stock; the unit price is priceInPaise × (1 − discountPercent/100); totals below ₹1 are rejected. One transaction writes a PLACED / PENDING order plus its items, then the Razorpay order is created and its id stored. A gateway failure marks the order CANCELLED / FAILED and returns 502.
  3. The app opens Razorpay Checkout with the returned razorpayOrderId, amountPaise and keyId.
  4. POST /customer/payment/verify with the three values checkout hands back. The server recomputes HMAC-SHA256(orderId|paymentId, keySecret) and compares with crypto.timingSafeEqual. A match moves the order to PAID / CONFIRMED; a mismatch marks it FAILED. Verification is idempotent and refuses an order belonging to another customer.

Order numbers look like NZ-<base36 timestamp>-<6 hex>, kept inside Razorpay's 40-character receipt limit. Note values are trimmed to 256 characters.

Background jobs

Three cron jobs in src/jobs/, all off unless ENABLE_JOBS=true. The guard is not caution for its own sake: these jobs write shared state, so two dev instances against one database would each raise the same alerts and each escalate the same markdown, and nodemon restarting on every file save would re-run them constantly. Timezone comes from JOBS_TIMEZONE (default Asia/Kolkata), and each run is wrapped so a job's failure can never take the API process down with it.

JobScheduleWhat it does
replenishment0 * * * *Flags stock by days of cover — how long stock on hand lasts at the rate the item is actually moving — and only when it is also selling faster than its own 7-day mean (×1.3). Raises LOW_STOCK / STOCKOUT
markdown-sweep*/30 15-21 * * *Escalates end-of-day discounts along a ramp from 15:00 to 21:00, toward each product's owner-set floor. Raises MARKDOWN_APPLIED
markdown-reset5 0 * * *Just after midnight, restores baseDiscountPercent — the owner's own pricing

Why the thresholds are relative

A flat "stock below N" rule is wrong for a marketplace where one shop sells three shawls a month and another sells forty loaves a day: the same threshold is either constant noise or a warning that arrives after the stockout. Cover is measured in days (CRITICAL ≤ 1, WARNING ≤ 3), and cancelled and unpaid orders are excluded from velocity — goods never handed over did not consume stock, so counting them would inflate the rate and cry wolf.

The markdown engine is the one piece of this system that rewrites a price a merchant chose, so it is opt-in per product via markdownEnabled and never passes markdownFloorPercent. Within a day discounts only ever move up, so a shopper who saw 30% off never finds it back at 20%.

Alerts are upserted, never appended. Identity is (shop, product, type) among rows that are not yet RESOLVED, so a scheduled scan refreshes one alert instead of turning one real problem into twenty-four identical rows a day. A resolved alert is deliberately not matched — the owner dealt with it, and the problem recurring later is genuinely new news.

Drafting a listing from a photo

The supply side's hardest problem is not technical: listing stock by hand is days of unpaid work for a shop with a few hundred lines, and it is the usual reason a marketplace never gets any supply. services/listingDraftService.js reads the packaging instead — one photo yields name, brand, net quantity, category and both descriptions, leaving the owner to confirm and type a price.

Why it never drafts a price

The schema has no price field and the prompt forbids naming any amount of money, including inside the descriptions. The asymmetry is deliberate: a wrong name is a nuisance the owner fixes in a second, while a wrong price costs them money on a real sale and loses the shop. If a later version reads a printed MRP it must land in a field the owner still confirms — never in the price itself.

Measured latency, and why there is a ceiling

On Google AI Studio's free tier the same request against the same image returned in 14 s once and was still running past 90 s another time. That is not a latency budget a counter-side interaction can be designed around, and with no ceiling the request never returns — leaving a shopkeeper holding a phone that looks frozen with no way back to typing. Hence GEMINI_TIMEOUT_MS: a fast, honest "fill it in yourself" beats an indefinite spinner. Whether a paid tier is steadier is untested.

In the app

Once a photo is chosen, the upload screen offers Fill this in from the photo — the one lime CTA on the screen, since it is the highest-intent action there. It sends the image inline as base64 rather than uploading first: the photo is still on the device at that point, and uploading every picked image would leave Cloudinary orphans for products the owner never finishes. It reuses CloudinaryService's existing compression so a phone photo doesn't become a multi-megabyte body.

Two rules in _readPacket matter more than the plumbing. It only fills a field the owner has not typed into, so re-reading a photo can never overwrite a correction they just made. And it only sets the category when none is selected. Everything it writes is an ordinary controller value — editable, clearable, and the controllers remain the source of truth on submit.

Server error text is written for API clients — "Set GEMINI_API_KEY" is not something to put in front of a shopkeeper — so ApiService logs the raw message and translates the code into counter-side copy ("That took too long", "Couldn't read that photo"). The screen appends the remedy, since that is a UI concern.

data/models/listing_draft.dart carries the response and has no price member at all, which is the client-side half of the same guarantee. test/listing_draft_test.dart pins the degraded shapes: an unpicked category stays null rather than defaulting, low-confidence fields surface in needsAttention, and a thin or empty response must not throw — the form still has to be usable by hand.

The endpoint deliberately does not write. A path that both reads a photo and inserts a row is one bad extraction away from a catalogue full of confident nonsense, so creation stays with POST /shop/add-product after the owner has seen the draft.

How "nearby" is computed

There is no PostGIS. Radius filtering is a raw Haversine expression injected as a Sequelize literal into the location_infos where-clause:

(6371 * acos(
    cos(radians(:lat)) * cos(radians(latitude))
  * cos(radians(longitude) - radians(:lng))
  + sin(radians(:lat)) * sin(radians(latitude))
)) <= :radiusKm

The same formula is mirrored in JavaScript in src/dto/productDto.js so the distanceKm each shop reports agrees with the set of rows the query returned. Product endpoints reuse it indirectly: _shopIdsNearLocation resolves the nearby shop ids first, then constrains products.shop_id. An empty result narrows the query rather than being ignored — "nothing nearby" is a real answer.

Filter precedence

city / state / pincode are ILIKE matches and combine with the radius when both are supplied. Supplying neither returns unfiltered results, which is why the client always sends coordinates.

Why the DTO layer exists

The Flutter models are generated by json_serializable with non-nullable casts — json['brand'] as String — against columns that are nullable in Postgres. Returning raw ORM entities threw on the client and leaked internal names (priceInPaise, avgRating) along with the password hash. src/dto/productDto.js is the single place where entities become the exact shapes the app parses.

Backend

Data model

Nineteen models plus one join table, all BIGINT auto-increment surrogate keys with snake_case columns. Associations are declared centrally in src/models/index.js — the model files themselves define only columns.

Two conventions to internalise

Money is always integer paise — price_in_paise, total_amount_paise, unit_price_paise. Nothing stores rupees or floats. And pg.defaults.parseInt8 = true is set at the top of models/index.js: without it every BIGINT id would serialise as the string "1" and break the typed client.

Flutter client

The app

A single Flutter app serving all three roles, structured feature-first with BLoC for state. There is no router package: navigation is Navigator.push with a custom shared-axis route, and the root widget picks a shell based on the restored session.

Startup — lib/main.dart

  1. FlutterNativeSplash.preserve holds the splash while work happens.
  2. SessionManager.instance.restore() loads every account saved on the device. This has to happen before the first profile fetch, because that fetch is what decides which home screen the app opens on.
  3. mainAsyncTasks() checks connectivity, then calls POST /user/me with the active account's token. It returns a Customer, a ShopModel1, a NoInternetModel, or null.
  4. The result and the has_seen_onboarding flag choose the home widget: onboarding, CustomerHomePage, ShopHomePage, or the offline screen. An unauthenticated visitor lands in the customer shell and browses as a guest.
  5. Two repositories and four BLoCs are provided above MaterialApp, so state survives tab switches.

Sessions on the device

SessionManager owns every account signed into on this device and which one is live, serialised under the nearzy_accounts key. Two jobs that are really one:

  • Switching. Signing out to try another account used to mean retyping a password. Sessions are kept per account, so switching is a tap and the previous account is still signed in when you come back.
  • Refreshing. accessToken renews the active token before handing it out, and refreshActive is what NearzyHttp calls when the server rejects one anyway. Both funnel through a single in-flight future, so twenty parallel requests hitting an expired token produce one refresh, not twenty — which matters because refresh tokens rotate, and racing refreshes would each invalidate the others and sign the user out.

Consumers listen for a SessionEvent: the shell rebuilds on signedIn, switched and signedOut, while refreshed is routine maintenance that must not disturb anything on screen, and expired carries the message explaining why a password is being asked for again.

Also in flutter_secure_storage, through SecureStorage: has_seen_onboarding, favourite_product_ids and recent_searches. Favourites are a client-only wishlist — there is still no server endpoint for them. jwt_token remains as the legacy single-token key that restore() migrates from, and normalizeToken still unwraps a token whether it arrives bare, JSON-quoted, or inside {"token": …}.

Launcher icon & splash

Both are generated, not drawn by hand. Why the sizes look arbitrary

Adaptive icons draw on a 108 dp canvas but launchers only ever show the central 72 dp, so a mark that should read at 62% of the visible icon has to be authored at 62% × 72/108 = 41.3% of the canvas. On top of that flutter_launcher_icons insets the foreground by 16% unless told otherwise, which is why adaptive_icon_foreground_inset: 0 is set. Getting both wrong at once is what made the old icon look like a small pin floating in a large dark square.

flutter_native_splash treats every source as 4×, so 1152 px = 288 dp, the Android 12 splash-icon canvas. With no icon background colour set, AOSP masks that canvas to a 192 dp circle — 768 px here — which is what the baked disc's 720 px sits inside. Conveniently this mark's circumscribed circle diameter equals its bounding-box height, so one number budgets against both.

Two OEM deviations the assets are shaped around

Both were found on HyperOS and both are the reason the sources look the way they do. First, windowSplashScreenIconBackgroundColor is a background, and the shell masks it with the launcher's own icon shape — on a device set to square icons the lime disc rendered as a lime square. Hence no background colour at all: the disc lives inside splash_logo_android12.png, where nothing can reshape it.

Second, the branding image is drawn at raw pixel size, ignoring density: the xxxhdpi asset's 117 px of glyphs measured 117 device px on a 2× screen, where the density-correct answer is 234. So the wordmark's on-screen size tracks the source's pixel dimensions rather than its dp size, and it renders roughly twice as large there as on a compliant device. Both are worth re-checking against a screenshot after any change to these two assets — a spec-correct source is not evidence of a correct result.

The wordmark cannot sit under the pin

Android 12+ masks the splash icon to a circle, so "Nearzy" goes in the OS branding slot at the foot of the screen rather than into the icon. Older Android gets the same treatment through a bottom-gravity layer in launch_background.xml, and iOS through a bottom-constrained image view in LaunchScreen.storyboard — identical on every platform. NearzySplashLogo in nearzy_logo.dart renders a richer animated version of the lockup, but nothing uses it: main.dart finishes its async work before runApp and drops the native splash immediately after, so there is no window for a Flutter-drawn one.

Two helpers do most of that work and should be reached for instead of hand-rolled equivalents: PressableScale for the press response, and CrossFade for every phase change. CrossFade exists because a bare AnimatedSwitcher keys its entries by the child's own key, so keyless children collide and two of them fading out at once throw "Duplicate keys found"; a monotonic revision keeps every entry distinct. Network images go through NearzyNetworkImage, never a raw Image.network.

Operations

Sharp edges

Things a newcomer would otherwise have to discover by debugging. Grouped by the kind of surprise, not by severity.

Authorization

Two writes trust the body, not the token

POST /customer/update-cart-items takes customerId from the request body and POST /customer/update uses body.id, so any authenticated customer can act on another customer's rows. /shop/add-product was the third and now resolves its shop from req.user; the payment routes, /shop/my-products and the inventory writes show the same intended pattern. These two are the remaining work.

Secrets

Two credentials have committed fallbacks

jwtService falls back to a literal JWT secret and adminService to a literal admin secret code when the env vars are missing. Both values are in the repository, so a deploy that forgets its environment is signing tokens with a public key.

Schema

No migrations — sync({ alter: true }) on every boot

Convenient locally, hazardous anywhere with real data: the models are the only schema definition, and a column rename becomes a silent drop-and-add. Worth replacing with sequelize-cli migrations before this runs anywhere shared.

Client bug

The uniqueness checks always answer "false"

ApiService.emailExists and usernameExists parse the response with bool.fromEnvironment(response.body), which reads compile-time environment declarations rather than the body. Both return false whatever the server said, so duplicate-email validation only surfaces later as a 400 from /register.

Unfinished

Reviews can be read but never written

The reviews table, its 1–5 validation and the unique (product_id, customer_id) constraint all exist, and avg_rating / review_count on products drive most of the ordering in the discovery endpoints — but no route creates one. Every rating in the app today came from seed.js.

Wire format

One endpoint still skips the DTO

/customer/location-specialities emits raw Sequelize rows in its AFFORDABLE section while every other product endpoint goes through toProductDto — /customer/affordable-products has since been converted. The client's _unwrap helper is deliberately lenient about it, but the field names differ, so anything new should use the DTO.

Wire format

/me is a POST that still accepts a body token

The four profile endpoints remain POST, and callerIdentity keeps reading a raw JWT out of the request body as a fallback for older clients — a path the auth middleware never validated. New code should rely on req.user and treat the body token as deprecated.

Config

The API host is compiled in

ApiConst.baseApiUrl is a hardcoded literal with a tunnel URL commented above it; the Cloudinary cloud name and API key sit in the same file. Any host change is a source edit and a rebuild.

Config

The dashboard looks broken until the jobs are on

ENABLE_JOBS defaults to off, and nothing else writes shop_alerts — so a fresh checkout shows a shop dashboard whose alert list is permanently empty, which reads as a bug rather than a setting. Run ENABLE_JOBS=true npm run dev, or call runReplenishmentScan() / runMarkdownSweep() directly; both are exported from jobs/index.js for exactly that.

Pricing

A cron job rewrites merchant prices

The markdown engine mutates discount_percent on live products between 15:00 and 21:00 and restores it at 00:05. It only ever touches products whose owner set markdownEnabled, and never passes markdownFloorPercent — that opt-in is the safety model. Worth knowing before debugging "why did this product's price change overnight".
